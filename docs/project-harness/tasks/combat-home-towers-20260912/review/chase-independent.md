## Findings in initial candidate

1. **P1 — Native wall return can arrive but never release the latch** (candidate lines 163–168, 260–268). Once Returning, the no-follow HomeX is frozen. Native Berserker.GoToWallRoutine re-reads GetGuardPosition when the return state starts; kingdom wall destruction/rebuild, override or side changes can therefore make its real destination differ from the frozen home by more than two. The actor arrives at the native destination, but the mod never releases Returning and keeps filtering every enemy. Accept a validated native GotoWall Position goal/arrival as the return destination, while retaining a stable pursuit anchor before the return begins. Do not force another random native return every frame.

2. **P1 — Return transition can clear an external droppable assignment** (candidate lines 265–268). Every state except Attack can be redirected, including GrabDroppable. The native OnChangeState explicitly clears droppableTarget when leaving state 5. A tool assignment arising while Returning is active can therefore be stolen and cleared by the mod's transition. Treat the external assignment as a reason to release/defer the mod latch and do not redirect GrabDroppable. The native change-state callback, rather than an explicit assignment in this helper, is what clears the task.

3. **P2 — Finite-only generic return validation accepts impossible homes** (candidate lines 165–168). GetGuardPosition returns a generic KeyValuePair<Side,float>; arbitrary finite garbage side/position values are accepted. Repository native-interop history records Sided<float> returning a finite `4.7e19`, so IsFinite alone does not close this risk. Validate Key as Left/Right and validate Value/home against directly read physical ground bounds, or avoid the generic return using verified scalar APIs. This review does **not** claim GetGuardPosition currently returns the same bad values: it identifies the missing defensive boundary and the relevant precedent. Unknown/unverifiable home must not create a return latch.

4. **P2 — Scanner replacement retains stale registrations and can erase current ownership** (candidate lines 95–99, 114–116, 203–204). Bind adds keys without removing old ones, so a living actor that has its scanner(s) replaced can accumulate more than the contracted one/three entries. Calling a stale scanner then fails Owns and Forget removes the entire actor, including valid replacement scanner mappings and its return latch. Prune obsolete keys during Ensure and remove only the stale key when that scanner fails the ownership test; preserve the current actor state.

Owned scanner fields and exact observer transform are verified before mutation. Scanner.Refresh explicitly targets its bool overload, and unrelated scanners stop at the dictionary lookup.
