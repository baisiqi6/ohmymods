## Findings

**P1 — one-frame refill window between scope exit and slot OnDestroy.** The operator's own open question is real. Teardown order is DeregisterObject → DontPersistInstance → SetActive(false) → `Destroy` (deferred to end of frame) → `finally` clears suppression. The slots remain in the Kingdom's list at `[rbx+278h]` until the deferred `OnDestroy` unregisters them. If anything else triggers `DistributeTowerArchers` in that window, it sees empty slots on a now-inactive tower and may station archers there — actors re-parented under an inactive root (hidden, though not persisted thanks to DontPersistInstance). Offline-only plus "needs another distribution trigger in the same frame" makes this low probability, but it is the main practical correctness gap. It cannot be closed by extending the scope (Destroy is deferred), so the honest options are accepting it with a note or verifying `DistributeTowerArchers` guards on slot activity in the full body.

**P2 — exact-Kingdom pointer assumption degrades silently.** Suppression only fires when the invoking instance is pointer-identical to `Managers.Inst.kingdom`. If native code holds a different Kingdom reference, suppression quietly fails open — which falls back to the old refill behavior, and the verify-exit gates then retain the tower. So the failure mode is safe (retention, not corruption), but the cleanup would silently stop working. Worth a one-line runtime log if the "retained … verify-exit/public-guard-reference" stage ever fires after deployment.

**P2 — statics assume single-threaded invocation.** `cleanupActive`/`suppressionKingdom` are plain statics; safe on the Unity main thread, and `ContextValid` gates on offline+auth so network threads shouldn't invoke distribution, but if any native path calls `DistributeTowerArchers` off-thread the flags race. Fail-open design keeps the worst case at "distribution not suppressed," so acceptable.

**Tests.** The four new tests genuinely exercise the shipped logic (not just mocks): the refill callback is modeled on every exit and asserted suppressed for all three, exact-kingdom vs other-kingdom vs null gating is checked, reentrant refusal returns no removals without poisoning the subsequent pass, and both a native exception and a post-exit eligibility rejection leave the scope cleared and the next cleanup working. They cannot cover actual Harmony patch installation or the real native callback chain — consistent with the stated "no claimed runtime success; E-copy startup pending."

**PASS with the P1 window acknowledged** — nothing here blocks proceeding to the controlled runtime check, and that check should specifically watch for archers assigned during the teardown frame.
