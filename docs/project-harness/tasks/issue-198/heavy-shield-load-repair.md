# Issue #198：盾卫读档身份校验修复

范围为宝石盾卫商店读档后显示“存档身份待核验，暂停购买”、无付款圆点。火枪手当前 17 份购买记录的首次失配原因仍未确认，本次不修改其业务逻辑，不关闭整个 Issue。

## 错误产生处

旧岛屿身份使用完整原生岛屿 JSON 的字节哈希。实际 Mac ARM64 读档时，`playTimeDays` 的数值表示发生 1 ULP 差异；其余岛屿数据保持一致，却被误判为未知身份。原始磁盘数据与旧记录精确匹配；已观察到的运行时差异发生在原生读档与再次序列化之间，尚未把转换责任细分到解析器或序列化器。没有证据表明游戏时序被修改。

## 修复责任与边界

- Payload 升到 v3，每岛显式记录 legacy/canonical 哈希类型，保留原存档键。新身份排除恰好三个顶层游戏时间字段，其余字段继续参与；旧记录不会仅因版本号而被重新标记。
- 旧原始数据在原生 `JsonUtility.FromJsonOverwrite` 加载边界只读捕获；原始 legacy 哈希必须精确成立，并再次匹配当前 Global 对象、原始 payload、岛屿上下文及当前 canonical 哈希。失败、嵌套、对象替换和不一致不产生证明，不修改原生参数或异常。
- 无已购权益的旧岛屿由已有加载生命周期做严格迁移；多个 campaign 副本与实际岛屿槽位必须同时成立。不能把付费或未知记录当作空岛，不通过清除权益、猜测 ULP、扫描补建或反复重写来解锁。付款继续等待真实持久化准备完成。

## 已完成验证

生产源码链接的 schema、身份、耐久、迁移与保存回归通过；受控 native transport 的旧付费证明→恢复→Stage/Prepare→冷读用例通过。它们不代表真实原生付费经济验收。

Mac ARM64 隔离原生用例已完成：无已购权益的旧记录保存退出后，独立重进为 Exact、身份就绪，原生店铺生成 5 个付款点。另一次原始旧存档加载中，原生源捕获→对象/键/岛匹配→legacy Exact 先于迁移介入成立。真实补丁归属、managed token 8/native token 7、唯一 GameAssembly 映像与入口 RVA `0x3a12290` 均核验。首次入口诊断因映像计数上限不足为 UNKNOWN，该结果保留；修正临时诊断上限后的独立窗口通过，不回改旧结论。各窗口结束后，最新存档、偏好、正常运行环境与游戏本体均按完整字节哈希恢复一致。

临时诊断代码已从最终源码删除。最终累计 Mac 构建 0 warnings / 0 errors，38 份资源和既有 Harmony 注解保持；与诊断关闭的已验源码比较，全部匹配签名的业务 IL 相同，仅恢复原三参数 Prefix 并移除诊断 helper。Prefix、Finalizer 和 TargetMethod 又与观察代码接入前的实现直接比对一致。

最终候选 SHA256：`023b254b4da5a54066b927446bfbc7e556c30be0ebf17043f9c415c6ef61cd33`。构建输入为 285 份、真实引用 161 份。

## 尚未完成

最终独立源码审查已通过，正在交付盾卫部分 PR；正常游玩 DLL 尚未替换。原生旧已购盾卫权益的实际扣款/战斗/保存往返、非 Global 与异常输入的完整原生传透、Windows/x86_64 ABI 和玩家正常入口体验未由本轮用例证明。火枪手失配仍单独保留在 #198。
