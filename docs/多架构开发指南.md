## 2. Mono vs IL2CPP：能力边界

### 2.1 能看到什么

```
                    Mono                          IL2CPP
                    ────                          ──────
Assembly-CSharp.dll │ .NET IL 字节码              │ C++ 原生机器码 (GameAssembly.dll)
                    │                              │
dnSpy / ILSpy 能读到 │ ✅ 类名                     │ ✅ 类名 (仅元数据)
                    │ ✅ 方法签名                  │ ✅ 方法签名 (仅元数据)
                    │ ✅ 方法体 (可读 C# 逻辑)     │ ❌ 方法体 (空 throw stub)
                    │ ✅ 字段名/类型/值            │ ✅ 字段名/类型 (无初始值)
                    │ ✅ 局部变量名                │ ❌
                    │ ✅ 控制流 (if/for/...)       │ ❌
```

### 2.2 能改什么

| 操作 | Mono | IL2CPP |
|---|---|---|
| 改数值常量 | dnSpy 改 IL，直接改方法体 | Harmony Postfix 改返回值 |
| 替换整个方法逻辑 | dnSpy 重写方法体 | Harmony Prefix 返回 false 跳过原方法 |
| 新增字段/类 | dnSpy 添加 (或 BepInEx) | BepInEx + `[RegisterTypeInIl2Cpp]` 注册 |
| Hook 方法执行 | Harmony (可选，也可直接改) | **只能** Harmony |
| 修改原始 DLL 文件 | ✅ (但 Steam 验证会还原) | ❌ (机器码不可编辑) |

## 4. Mono 侧开发流程 (2.0.1 / 2.1.0)

### 4.1 dnSpy 直改 DLL (硬改模式)

```
适合：深度改造现有系统、小范围逻辑修改

1. 用 dnSpy 打开 Assembly-CSharp.dll (先备份！)
2. 找到目标方法 → 编辑方法体 (C#)
3. 编译 → 保存模块 → 覆盖游戏文件
4. 启动游戏测试

优点：所改即所得，不依赖运行时框架
缺点：游戏更新冲掉改动；Steam 验证还原文件；多人协作困难
```

### 4.2 BepInEx Mono 插件 (推荐)

```
适合：所有 mod，尤其是要发布的

1. csproj 用 -c BIE6_Mono 配置
2. 引用 deps\BIE6_Mono\ 下的程序集
3. 继承 BaseUnityPlugin
4. Harmony 做运行时 Hook (可选，因为也能直接改 DLL)
5. 编译产物放 BepInEx\plugins\
```

### 4.3 反编译当说明书

```
dnSpy 打开 Assembly-CSharp.dll
→ 导出项目 (File → Export to Project)
→ 得到完整 C# 源码 (变量名丢失，但逻辑可读)
→ 作为 IL2CPP 侧开发的参考
```

## 5. IL2CPP 侧开发流程 (2.4.0)

### 5.1 类型发现：Rosetta Stone 技术
> **前置条件**：类型发现脚本内部调用 `ilspycmd`，需先安装：
> `C:\Users\ADMIN\dotnet8\dotnet.exe tool install -g ilspycmd`
> 确保 `%USERPROFILE%\.dotnet\tools` 在 PATH 中。


```
核心思想：IL2CPP 的方法体读不到，但类名/方法签名读得到。
         Mono 版能读到完整逻辑。
         游戏版本间逻辑变化不大 → 用 Mono 反编译当 IL2CPP 的说明书。

步骤：
1. search_types.py 定位类
   → python search_types.py interop\Assembly-CSharp.dll "Upgrade"

2. get_type_members.py 看成员
   → python get_type_members.py interop\Assembly-CSharp.dll "PayableUpgrade"

3. 对照 Mono 反编译理解逻辑
   → dnSpy 打开 Mono 版 Assembly-CSharp.dll → 找同名方法 → 读 C# 源码

4. 写 Harmony Hook
   → 用签名信息构造 [HarmonyPatch] → 实现你的逻辑
```

### 5.2 Harmony Hook 模式 (唯一改法)

**Postfix — 改返回值 (最常用)**

```csharp
[HarmonyPatch(typeof(SomeClass), nameof(SomeClass.GetCost))]
[HarmonyPostfix]
public static void GetCostPostfix(ref int __result)
{
    __result = 5;  // 把返回值改成 5
}
```

**Prefix — 拦截 / 替换方法**

```csharp
[HarmonyPatch(typeof(SomeClass), nameof(SomeClass.SomeMethod))]
[HarmonyPrefix]
public static bool SomeMethodPrefix(SomeClass __instance)
{
    // 返回 false = 跳过原方法，完全由你的代码接管
    // 返回 true  = 你的 Prefix 执行后，原方法照常执行
    DoMyThing(__instance);
    return false;
}
```

**观察游戏生命周期 (BeachMapper.cs 范例)**

```csharp
[HarmonyPatch(typeof(Beach))]
public static class BeachNotifier
{
    [HarmonyPatch(nameof(Beach.Start))]
    [HarmonyPostfix]
    public static void Start(Beach __instance)
    {
        // 游戏创建 Beach 组件时触发，可在此采集/标记对象
    }
    [HarmonyPatch(nameof(Beach.OnDisable))]
    [HarmonyPrefix]
    public static void OnDisable(Beach __instance)
    {
        // 组件销毁时触发
    }
}
```

### 5.3 IL2CPP 下注册 MonoBehaviour

IL2CPP 不允许动态类型，自定义 MonoBehaviour 必须注册进 il2cpp 域。**三步缺一不可**，否则编译通过但 Awake/Start/Update 永不触发（新手最容易踩的坑）：

**Step 1 — 标记类 + IntPtr 构造函数**

```csharp
#if IL2CPP
using KingdomMod.SharedLib.Attributes;  // SharedLib 自定义特性，非 Il2CppInterop 原生那个
#endif

#if IL2CPP
[RegisterTypeInIl2Cpp]
#endif
public class MyHolder : MonoBehaviour
{
#if IL2CPP
    public MyHolder(IntPtr ptr) : base(ptr) { }  // IL2CPP 要求的构造函数
#endif
    // Awake/Start/Update/OnGUI 等生命周期方法可正常使用
}
```

**Step 2 — 在插件 Load() 中注册程序集**

```csharp
#if IL2CPP
    public override void Load()
    {
        RegisterTypeInIl2Cpp.RegisterAssembly(Assembly.GetExecutingAssembly());
        // 然后创建实例：
        var go = new GameObject("MyHolder");
        UnityEngine.Object.DontDestroyOnLoad(go);
        go.AddComponent<MyHolder>();
    }
#endif
```

> ⚠️ `[RegisterTypeInIl2Cpp]` 只是标记，**不会自动注册**——必须显式调用 `RegisterAssembly()`。KingdomMod 四个 mod 的 Plugin.cs 全部如此。

### 5.4 跨架构插件入口

```csharp
using BepInEx;
using BepInEx.Logging;

#if IL2CPP
using BepInEx.Unity.IL2CPP;
#else
using BepInEx.Unity.Mono;
#endif

[BepInPlugin(GUID, NAME, VERSION)]
[BepInProcess("KingdomTwoCrowns.exe")]
public class MyPlugin :
#if IL2CPP
    BasePlugin          // IL2CPP: 入口是 Load() 方法
#else
    BaseUnityPlugin     // Mono: 入口是 Awake() 方法
#endif
{
#if IL2CPP
    public override void Load() { /* 初始化 */ }
#else
    private void Awake() { /* 初始化 */ }
#endif
}
```

## 7. 迁移路线图：Mono mod → IL2CPP

### 场景：你在 2.0.1 Mono 上用 dnSpy 改了某方法，想移植到 2.4.0 IL2CPP

```
Step 1: 理解原改动
├── dnSpy 打开 Mono 版 Assembly-CSharp.dll
├── 找到你改的方法，记录：
│   ├── 类名 + 命名空间
│   ├── 方法签名（参数、返回值）
│   ├── 改了什么（哪行逻辑、改成什么值）
└── 输出：一份 "改动清单"

Step 2: 确认 IL2CPP 版类型存在
├── search_types.py 查同名类
├── get_type_members.py 确认同名方法存在
├── 如果签名变了（参数/返回值）→ 记录差异
└── 如果类/方法不存在（版本间被重命名/删除）→ 需要逆向定位替代品

Step 3: 选择 Hook 策略
├── 改数值 → Postfix 改返回值
├── 改条件分支 → Prefix 拦截，自行实现逻辑
├── 加新功能 → Prefix/Postfix 注入，不影响原方法
└── 删原有功能 → Prefix return false 跳过

Step 4: 写代码
├── 新建 csproj (双架构起点抄 BetterPayableUpgrade；HelloPlugin 仅作 IL2CPP 冒烟测试)
├── 写 HarmonyPatch
└── #if IL2CPP / #if MONO 条件编译吸收差异

Step 5: 编译 + 测试
├── dotnet build -c BIE6_IL2CPP (或 Debug)
├── 产物自动复制到 BepInEx\plugins\
├── 启动游戏 → 看 BepInEx\LogOutput.log 确认加载
└── 游戏内验证行为

Step 6: 产出 Mono 版 (可选)
├── dotnet build -c BIE6_Mono
├── 放到 2.0.1 / 2.1.0 的 BepInEx\plugins\
└── 同一份代码，两个架构都覆盖
```

### 常见迁移陷阱

| 陷阱 | 原因 | 解法 |
|---|---|---|
| 泛型方法 Hook 失效 | IL2CPP 泛型需要具体实例化 | 用 `AccessTools.Method` + 反射构造 |
| 字段类型不匹配 | IL2CPP 包装类型 (`Il2CppSystem.*`) | 用 interop 程序集中的类型，非标准 .NET |
| 内联方法无 Hook 点 | 编译器内联，无独立方法体 | Hook 调用方而非被内联方法 |
| MonoBehaviour 不触发 | IL2CPP 未注册 | 见 §5.3 三步：标记 + RegisterAssembly + 实例化 |
| 协程崩溃 | IEnumerator 在 IL2CPP 下行为不同 | 用 `Il2CppSystem.Collections.IEnumerator` |
| 版本间方法消失 | 2.3+ 新菜单/活动代码 | search_types 重新定位，或 Ghidra |

## 8. 版本追踪与维护

### 8.1 游戏更新后的检查清单

```
[ ] 检查 BuildInfo.txt 确认版本号变化
[ ] search_types.py 确认你 Hook 的类/方法仍存在
[ ] 启动游戏，看 LogOutput.log 有无红色错误
[ ] IL2CPP 版：看是否需要重新生成 interop 程序集
    (游戏更新后 GameAssembly.dll 变，Cpp2IL 要重跑)
[ ] Mono 版：通常不受影响（除非方法签名变了）
```

### 8.2 interop 程序集更新

```
IL2CPP 游戏更新后：

1. BepInEx 首次启动会自动跑 Cpp2IL 重新生成 interop
2. 如果 Cpp2IL 崩溃（见 BepInEx issue #1117）：
   ├── 用 KingdomMod 提供的 Cpp2IL.Patch
   └── 下载地址：KingdomMod releases → Cpp2IL.Patch.zip
3. 更新 deps\KTC-ModDevLibs 里的引用：
   ├── 从游戏 BepInEx\interop\ 复制最新 dll
   └── 或等 KTC-ModDevLibs 仓库更新后同步
```

### 8.4 存档安全

> ⚠️ 改经济/进度类 mod（如 BetterPayableUpgrade 改金币上限与升级价格）可能**污染存档**。

```
风险：
- 改数值后存档保存了 mod 值，卸载 mod 后存档可能不可用或行为异常
- 联机/CO-OP 模式下双方必须装相同 mod，否则 desync
- 跨版本迁移存档有损坏风险（2.0 → 2.4 不兼容）

建议：
- 进 mod 版前备份存档目录： %USERPROFILE%\AppData\LocalLow\
- 卸载 mod 前先在游戏内还原原始数值
- 联机双方对齐 mod 列表
```

### 8.5 IL2CPP 深度逆向（当 Rosetta Stone 不够用时）

当目标方法在 Mono 版不存在（2.2.0+ 新增）或逻辑变化太大，Rosetta Stone 参考失效时：

```
工具链：Cpp2IL（元数据/地址映射）→ Ghidra（机器码分析）

1. Cpp2IL 生成 interop 程序集时，同时输出方法地址映射
   → 每个方法的 RVA（相对虚拟地址）记录在元数据中

2. Ghidra 加载 GameAssembly.dll
   → 用 Cpp2IL 的地址映射定位目标函数
   → Il2CPP 调用约定：前两个参数是 MethodInfo* 和 this 指针
   → 方法体内的对象操作通过 il2cpp_runtime_* 系列调用

3. 能读到什么：
   ├── 控制流（if/for/switch 的机器码形态）
   ├── 函数调用序列（调用哪些其他方法）
   ├── 常量值（硬编码的数值/字符串）
   └── 字段访问偏移

4. 局限：
   ├── 变量名全丢失（只有寄存器/栈偏移）
   ├── 泛型实例化会产生大量相似函数，定位困难
   └── 编译器优化（内联/常量折叠）可能改变代码结构
```

## 10. 开发原则

1. **Mono 开发，IL2CPP 移植** — Mono 上迭代快（dnSpy 秒改秒测），逻辑验证后再用 Hook 移植到 IL2CPP
2. **一份代码两个架构** — 用 `#if` 条件编译，共享逻辑放 SharedLib，KingdomMod 工程就是模板
3. **Harmony 优先于硬改** — 即使在 Mono 上也尽量用 BepInEx + Harmony，不污染游戏文件，游戏更新不丢
4. **类型签名是契约** — 记录你 Hook 的每个方法的完整签名，游戏更新后第一时间核对
5. **Mono 反编译是 IL2CPP 的说明书** — 始终保留一份可读的 Mono 反编译源码作为参考
