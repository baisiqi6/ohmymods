# Hero shop verification

`dotnet run --project Core.csproj`: 54 assertions exercise the actual production payment ticket (payer matching, complete coin count, final native eligibility, cancellation, duplicate callbacks, next purchase), bounded placement (centre, blocked centre, borders, no gap, invalid/unknown bounds, 81-call cap), the ground baseline policy (a same-world active native shop root is accepted as-is for positive, negative and zero y; other-world, inactive, non-finite or absent references are refused so creation defers instead of guessing a height) and the retention policy `HeroShopRetention.Decide` that `Tick` runs: a same-world Menu pause keeps the existing shop (`Keep`, no clear, no create), `CanServe` — the payment gate — stays false in the Menu and true only while playing, creation is deferred to `Playing`, and feature-off, network/authority loss, a foreign world, a broken header, a destroyed scene or an unreadable context past the bounded hold still produce their clear outcomes.

`powershell -File Wiring.ps1` reads the built `il2cpp/bin/Debug/KingdomEnhancedMod.dll` with Mono.Cecil (metadata only, no game start) and fails unless `HeroShop.Tick` calls `HeroShopRetention.Decide`, `HeroShop.CanPurchase` calls `HeroShopRetention.CanServe`, and `HeroShop.Observe` still reads the native game state: the pure policy is the code the frame loop runs, not a test-only copy.

`dotnet build Interop.csproj`: compiles the actual HeroShop.cs against the correct E-drive 2.4 interop and installed Il2CppInterop runtime. No game installation or process startup. Stubs only supply the other MOD slice/config/logging contract.

The 512×80 original artwork consists of four 128×80 frames at 32 PPU, pivot (0.5, 0.025). One shared texture/four cached sprites; no frame-time texture generation.

Runtime gates: native IPayableComponentOwner interface registration and its three method dispatches are preflighted before shop activation. A real CRPCStamp and NativePostbox SemiStatic registration must match both native lookup tables. The original PayableComponent handles payment/coin cancellation. The object never enters ShopPlanner or receives Persistent.

Grounding: the shop root y is copied from an active native PayableShop root that lives inside the current world's GameLayer hierarchy (2.4 resources: prefab root y = 0.875 with the body SpriteRenderer on that same root, pivot.y = 0, PPU 32; world scope uses the existing `IsChildOf(world.gameLayer)` test from AutoRestockCounts/SiegeAmmoCounts). Other worlds, pooled/inactive stubs and renderer children are never a baseline, and a missing reference defers creation instead of falling back to the GameLayer y. The MOD art pivot (0.5, 0.025) already marks its 2 px contact margin, so no extra raise is applied; the one-time `ground source= native-root rootY= bodyOffset= groundY= finalY=` log records the choice.

The owner rejects native Completed CanPay unless the current local player owns this completing payable, has all eight floating coins and an unconsumed transaction receipt. Native UpdatePayState then cancels before TransactionComplete when evidence is missing. A bypassed malformed callback returns its actual floating objects through native DropFloatingCurrency; it never assumes eight coins. A previously settled callback cannot grant or refund twice.

Actual 2.4 inspection: Player.UpdatePayState RVA 0x69b2b0 (2560 bytes) calls Payable.TransactionStarted at 0x69b85e and Payable.TransactionComplete at 0x69b9b7; the preceding 0x69b995 virtual CanPay gate remains native. The three-argument UpdatePayState includes the touch flag. No PayImmediate method exists in the actual Assembly-CSharp interop's top-level type methods (nor in the 2.1 reference); no separate mobile payment path is claimed tested.

Inactive setup safety: PayableComponent has no Awake override in 2.1 reference or 2.4 interop. Actual Payable.Awake RVA 0x6658a0 initializes coin/highlight arrays and transform, not owner/RPC fields. Registration while inactive initializes actual native RPC fields first; after activation, native Awake/OnEnable run before eligibility. Header failure is closed. This still needs live Unity validation.

Retention: a native Menu pause (`Game.State.Menu`, the world still loaded, `Time.timeScale = 0`) is not a loss. `Tick` keeps the same shop object, body, banners and SemiStatic registration, blocks new payment (`forceBlockPayment = true`; `CanPurchase`/`CanPay` stay false because they serve only the policy's `Active` outcome) and cancels an open native transaction exactly once through the native `CancelTransaction`/`DropFloatingCurrency` path so floating coins return. Only `Game.State.Playing` may create a shop. Feature-off, online/authority loss, a foreign kingdom/GameLayer, a header mismatch or a truly gone scene still clear immediately, each with its own bounded `clear reason=...` log line; unreadable context or any game state other than exact Playing/Menu clears immediately. No timeScale logic is added.

Call `HeroShop.Tick()` from the existing panel update, `Clear(reason)` at shutdown, and `CancelPendingTransactions()` in the existing native Save prefix before wallet serialization. The save callback must not swallow cancellation failure and then serialize the wallet with suspended coins.

Not verified by these tests: live interface injection, native Awake/OnEnable order, full native coin-slot visual flow and refund persistence, scene teardown ordering, real placement/rendering, two local players, original-game save/load round trip, and the live pause path itself — that a real Menu pause keeps the same instance and that a mid-payment pause returns the coins through the native cancellation. Online hero/shop remains disabled. No game was started or DLL deployed by this worker.
